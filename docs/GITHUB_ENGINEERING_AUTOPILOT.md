# MARSEL ROAPP — GitHub Engineering Autopilot

**Назначение:** единый рабочий регламент инженерной работы GitHub для проекта **MARSEL ROAPP**. Этот документ дополняет `00_PROJECT_CONTROL/GITHUB_GOVERNANCE.md`, не заменяя его.

## 1. Канонический контур

- Канонический репозиторий: `atalanrafael-jpg/MARSEL-ROAPP`.
- Каноническая ветка интеграции: `main`.
- Название системы: **MARSEL ROAPP**; MARSEL — бизнес-контур, ROAPP — технологический контур.
- Не создавать параллельный источник истины. Исторические репозитории и ветки сначала классифицировать; не удалять автоматически.
- Текущий HEAD, файлы и результаты CI важнее старых отчётов и сообщений.

## 2. Обязательный цикл выполнения

`READ → VERIFY CONTEXT → CLASSIFY RISK → PLAN → BRANCH → IMPLEMENT → TEST → REVIEW DIFF → PR → CI/SECURITY CHECKS → REVIEW → MERGE (AUTHORIZED) → VERIFY MAIN → RECORD CHECKPOINT`

Для каждого этапа фиксировать доказательства. Если инструмент или разрешение недоступны, указывать конкретный блокер; не имитировать результат.

## 3. Проверка перед изменением

1. Получить фактические URL/ID репозитория, default branch, текущий HEAD SHA и последние коммиты.
2. Прочитать README, этот регламент, master-control документ и относящиеся к задаче контракты.
3. Проверить открытые Issues/PRs, статус и SHA проверок, workflow, незавершённые изменения и связанные зависимости.
4. Убедиться, что задача не дублирует существующую Issue/реализацию.
5. Сформулировать причину, минимальный diff, критерии приёмки, тесты, риск и план отката.

## 4. Правила разработки

- Изучить существующую архитектуру и тесты до изменения поведения.
- Использовать минимальные совместимые изменения; добавлять регрессионный тест для подтверждённой ошибки.
- Не удалять исторические данные, рабочие функции или старые реализации без доказательства ненужности и плана восстановления.
- Не вводить фиктивные API, поля, ID, статусы, связи и возможности.
- Документировать изменения контрактов, архитектуры, поведения и эксплуатационных требований.
- Не помещать ключи, токены, персональные данные и содержимое секретов в код, Git, артефакты или логи.

## 5. CI/CD и безопасность

Проверять результат на конкретном commit SHA, а не только название workflow или статус старого запуска. Разбирать упавшие jobs и шаги; различать `success`, `failure`, `cancelled`, `skipped`, `pending` и отсутствие запуска.

Проверять:
- тесты, линтеры, типы и сборку, если они применимы;
- зависимости и уязвимости;
- секреты и правила их использования;
- минимальные `GITHUB_TOKEN` permissions;
- сторонние Actions и фиксацию версий;
- branch protection/rulesets и обязательные проверки;
- миграции, совместимость схем и восстановление.

Зелёный общий workflow не доказывает успех пропущенного шага. Успешный CI не доказывает готовность production.

## 6. ROAPP и production safety

- Live-аудит RO App — READ-ONLY по умолчанию.
- Использовать только официально подтверждённые API-контракты; неизвестный endpoint — `NOT_VERIFIED`.
- Не угадывать идентификаторы и не удалять дубликаты автоматически.
- Production WRITE остаётся отключённым, пока не доказаны backup/export, независимое восстановление, целостность, полное чтение, сверка ссылок/дубликатов, dry-run, идемпотентность и откат; требуется отдельное явное разрешение.
- Не выполнять необратимые миграции, слияние PR, закрытие Issues, удаление веток, ротацию ключей или production-деплой без соответствующего разрешения.
- При неполных или конфликтующих доказательствах результат — `REVIEW_REQUIRED`, `BLOCKED` или `NOT_VERIFIED`, не `PASS`.

## 7. Issues и Pull Requests

- Связывать исправление с существующей Issue, если она есть; не создавать дубликаты.
- В PR указывать: что изменено, почему, тесты и их результаты, SHA, риски, влияние на production и доказательства.
- Проверять полный diff, конфликты, review и все обязательные проверки.
- Не обходить защиту ради зелёного статуса.
- Не сливать PR автоматически в рамках этого регламента; сначала убедиться, что требуемые проверки и разрешения выполнены.

## 8. Формат контрольной записи

Для каждого существенного изменения фиксировать:

- **Цель / Issue / PR**
- **Исходное состояние:** репозиторий, ветка, HEAD SHA
- **Причина:** подтверждённая ошибка или требование
- **Изменения:** файлы и краткое описание diff
- **Проверки:** команды/workflows, commit SHA, итог каждого шага
- **Безопасность:** секреты, права, production impact
- **Остаточные риски и блокеры**
- **После изменения:** новый HEAD SHA и доказательства
- **Следующий безопасный шаг**

## 9. Статусы

- `VERIFIED` — подтверждено актуальными доказательствами.
- `DONE` — действие выполнено и результат перепроверен.
- `PREPARED` — подготовлено, но не внедрено.
- `BLOCKED` — указан конкретный блокер.
- `FAILED` — проверка/действие завершились ошибкой.
- `NEEDS USER ACTION` — требуется авторизация или действие пользователя.
- `NOT VERIFIED` — достаточных доказательств нет.

## 10. Основной принцип

**Сначала проверить, затем изменить, после этого повторно проверить и зафиксировать доказательства.** Не заявлять о подключении, синхронизации, backup, тестировании, CI, deploy или завершении без прямого подтверждения.
